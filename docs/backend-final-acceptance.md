## 真实故障演练

命令：`python3 scripts/verify-recovery.py`。脚本每次新建随机项目、凭据和端口，构建当前源码，使用独立 MySQL/Redis 数据卷，完成后删除本次测试资源。

| 场景 | 操作与断言 |
| --- | --- |
| 审计归档时强制退出 | 锁住 op_log 表；真实 HTTP 新增字典，确认 audit_outbox 已提交且归档 INSERT 被阻塞；SIGKILL 后端后待处理记录仍存在 |
| 审计恢复 | 释放表锁并重启，确认 outbox 清空、正式日志恰好 1 条；再次重启仍为 1 条 |
| Redis 故障与后端崩溃 | 先缓存旧字典，停止 Redis，经 HTTP 提交新值；确认数据库新值和待补偿记录，再 SIGKILL 后端 |
| 故障持续期间重启 | 只启动后端，验证 Redis 仍为 exited；经 Nginx 登录态查询成功，补偿任务仍保留 |
| Redis 恢复 | 只启动 Redis，等待补偿任务清空；HTTP 返回新值，直接读取缓存也为新值 |
| 指标采集 | promtool 校验配置与规则；实际查询 up=1 及 JVM 内存指标 |
| 告警生命周期 | 停止后端，等待真实 30 秒告警转为 FIRING；启动后端后 up 恢复为 1，告警消退 |

这些断言覆盖受控崩溃点，不承诺任何故障组合下都零丢失。MySQL 整体不可用时审计仍只能记录错误日志，Redis 缓存仍为最终一致。
