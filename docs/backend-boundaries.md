# 后端业务边界审查 · 2026-09-28

## 本轮结论

复现并修复登录失败计数与锁定、目标用户写入与角色分配的竞态。保留模块化单体结构，没有修改前端、表结构或接口契约，也没有提交、推送或部署。

图谱工具本轮未提供，使用源码与调用关系检查作为替代。审查入口包括 AuthController → AuthService，以及 SystemController → SystemService → DataScope / 数据访问；同时复核审计 outbox 和缓存补偿的事务边界。

## 先复现，再修复

### 登录失败计数与锁定

原实现中，AuthService.login 持有用户行锁校验密码，抛错后事务结束；AuthController 捕获 401，再调用另一个事务写失败计数。两次事务之间存在窗口，成功请求和后续失败请求可以穿插，登录服务自身也不保存失败计数。

旧代码上的测试结果：

- 8 个同时发起的错误密码 HTTP 请求，本应 5 个 401、3 个 429，实际 8 个全部 401。
- 将已有锁定设置为过期后再次输入错误密码，失败次数从 5 变成 6，未开始新的尝试窗口。
- 直接调用登录服务并收到错误密码异常后，数据库失败计数仍为 0。

修复：在同一个 `SELECT … FOR UPDATE` 事务中完成锁定检查、密码校验、失败计数更新或成功会话签发。只对专用 `LoginRejected` 异常设置 `noRollbackFor`，使预期的认证拒绝提交计数；数据库或签名异常仍回滚。删除 Controller 的第二次计数调用。锁定到期后从 1 重新计数，锁定中的请求保持截止时间不变。

### 用户变更与角色分配

原实现先检查目标用户范围及高权限角色，随后查询、编码密码并写入。管理员的角色分配没有与该链路共同持有用户行锁，可以在检查结束后先提交高权限角色，留下基于旧授权判断写入的窗口。

MySQL 回归测试通过真实 HTTP 发起主管修改，在密码编码阶段用 Mockito spy + CountDownLatch 暂停线程，此时数据范围和高权限保护检查均已完成。并行请求管理员分配角色：旧实现会在主管修改未结束时完成；修复后必须等待主管提交。随后再次由主管修改该目标，返回 403。

修复：在修改、删除、分配角色和个人改密事务中，先锁定目标用户行，再进行查询和校验。同一目标的角色分配和用户修改遵循数据库锁顺序，避免检查到写入之间被这些操作插入。MySQL 的普通读取快照在取得锁后建立。

注意：这是目标用户级串行化，不是全系统权限全局锁。慢密码计算会延长同一用户的锁持有时间；新增写入入口必须遵守相同规则。

## 审查边界与后续风险

- 当前用户的 Actor 在请求入口解析。操作者自身权限撤销、部门树变更不会主动取消已进入业务流程的请求；本轮没有实现任意权限变更瞬间中止全部在途请求。需明确该业务语义后，再设计统一的授权版本或锁协议。
- AuthService.resolve 分多次查询用户、权限和范围，尚未为跨查询的一致性快照建立专门并发验收。
- 角色分配与用户写入的测试覆盖一个受控交错时序；不等于所有并发操作、死锁恢复和吞吐均已验收。
- 审计注解当前位于 Controller，服务事务返回后才记录结果；已有失败回滚审计测试继续通过。outbox 转存与删除在同一事务内，行锁串行处理。数据库整体不可用时，切面仍只输出错误日志，不能保证零丢失；未做进程崩溃、多实例实测。
- 缓存补偿重复执行删除具有幂等性，已有 Redis 故障恢复测试通过；仍为最终一致，未验收多实例竞争和任意旧值回填时序。
- 测试使用 local 配置启动并覆盖数据库连接，生产密钥、反向代理、网络策略及部署未纳入本轮。
